3. CONCERT DISPLAY - INDIVIDUAL vs GROUPED
================================================================================

CURRENT BEHAVIOR: STRICTLY INDIVIDUAL CONCERTS

Each concert is displayed as a single unit:
  1. One <li class="concert-item"> per concert
  2. One poster image per concert
  3. One program text block per concert
  4. No grouping of movements or sub-concerts

PROGRAM DISPLAY:
  - Format: Single "program" field from database
  - Rendering: <pre> tag preserves multi-line formatting
  - Example:
    I. Allegro con brio
    II. Andante cantabile
    III. Minuetto - Trio
    IV. Finale - Presto
  
  - This is UNSTRUCTURED TEXT - no way to:
    - Link specific movements to movement data
    - Display movement durations separately
    - Show movement tempi as structured data
    - Search/filter by movement


GROUPING LOGIC:
  - Concerts grouped by YEAR only
  - grouping in controller: buildPastByYear()
  - grouping in template: concertsByYear array
  - NO grouping by work, composer, or movements

4. DATA STRUCTURE - CONCERTS WITH MOVEMENTS
================================================================================

CURRENT DATABASE TABLES:

concerts table:
  - id, title, date, location
  - poster_cloudinary_id, poster_local_filename
  - is_future, program_notes
  - Single "program" field stores all program info

concert_program table:
  - concert_id → work_id relationship
  - Stores complete works, NOT individual movements
  - No way to reference specific movements

works table:
  - id, composer_id, category_id
  - title, subtitle, catalogue, work_key
  - No movement information

concert_performers table:
  - concert_id, role (orchestra/conductor/soloist), name, instrument
  - Aggregated into view_concert_personnel_agg for display

concert_extra table:
  - concert_id, notes, youtube_url


PROBLEM:
  - concert_program links concerts to ENTIRE works
  - No table exists for movements within a work
  - Program information stored as single text string
  - No structured way to represent multi-movement pieces

8. KEY INSIGHTS
================================================================================

1. TWO-MODAL SYSTEM:
   - Year modal (z-index 9990): Filters concerts by year
   - Lightbox modal (z-index 9999): Shows individual concert details
   - Lightbox overlays year modal for detailed viewing

2. DYNAMIC YEAR MODAL:
   - Not pre-rendered in HTML
   - Created by JavaScript when year pill is clicked
   - Content copied from hidden DOM year panels
   - Allows interactive browsing without page reload

3. PRE-RENDERED DETAILS:
   - All concert details embedded in hidden DOM
   - concert-full-details divs populated at page load (SSR)
   - Copied to lightbox on demand (no server call needed)
   - Fast UI interactions, good for performance

4. SERVER-SIDE ENRICHMENT:
   - Controller fetches and enriches all data before templating
   - Merges: concerts + personnel + extras + programs
   - No API calls for details (all pre-loaded)
   - Good for SEO, potentially heavy initial payload

5. MOVEMENT LIMITATION:
   - No structured movement data currently
   - All program info stored as plain text in "program" field
   - Migration for movement support exists but unused
   - Concerts with multi-movement works not properly modeled

6. RESPONSIVE DESIGN:
   - Modals adapt to mobile with CSS media queries
   - Poster layout: 2-column desktop → 1-column mobile
   - Grid-based card system scales automatically
   - Touch-friendly close button and pill navigation

7. ACCESSIBILITY FEATURES:
   - role="dialog", aria-modal="true" on modals
   - aria-label and aria-labelledby on elements
   - Focus management (focus moved to modal on open)
   - ESC key support for closing modals
   - Keyboard navigation for pill buttons (Enter/Space)
